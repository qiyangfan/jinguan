# 支付订单超时:方案谱系与取舍

> 订单超时的职责拆解:①**资金正确性**——过期订单绝不可支付入账;②**状态及时性**——
> 过期订单尽快可见为 EXPIRED(报表/对账)。两件事的可靠性要求完全不同,方案因此分层。

## 双保险架构(当前实现)

```
L1 回调守门(懒过期,资金正确性)            L2 收敛扫描(状态及时性)
handleCallback:                             PaymentExpiryScheduler(@Scheduled)
  order.isExpired(now)                        findOverdue(CREATED, expires_at<now, batch)
  → 过期:抛 OrderExpired(409)                → expire() → saveAll
  → 不过期:markPaid + 发布入账事件            → 满批循环推进(游标批量)
```

**核心原则:L1 保证正确性零依赖调度器**——扫描任务死了、延迟了、多实例重复了,
过期支付都不可能入账;L2 只影响 EXPIRED 状态出现的及时性,延迟无害。
L2 的 UPDATE/迁移天然幂等(状态条件限定),多实例并发执行无重复副作用。

## 方案谱系与取舍矩阵

| 方案 | 正确性机制 | 优点 | 缺点 | 适用规模 |
|---|---|---|---|---|
| **懒过期 + DB 扫描(当前)** | 回调守门比对 expires_at,零依赖调度 | 零新基础设施;重启天然恢复(状态在 DB);实现/测试面小 | 状态及时性受扫描间隔限制;大表扫描需索引与批量 | 单实例,订单 ≤万/天 |
| MQ 延迟消息(RocketMQ 延迟级别/RabbitMQ TTL+DLX) | 消息触发关闭,broker 持久化 | 精准延迟;投递可靠;解耦 | 引 broker 运维;消息丢失需对账兜底(仍要扫描) | 订单万/天以上,已有 MQ |
| 时间轮(HashedWheelTimer) | 内存调度,启动扫表恢复+扫描兜底 | 精准高效;海量定时任务 | 不持久化(重启丢任务,必须配扫描兜底);复杂度高 | 单机海量定时任务(≥10万级) |
| xxl-job 分布式调度 | 调度中心扫表分片 | 集中式管理;分片广播 | 调度中心重部署;对单服务是重依赖 | 多服务共享调度平台 |

**取舍结论**:正确性由 L1 守门承担后,L2 只剩"定时批量更新"这一简单问题——
Spring `@Scheduled` 即最优解;MQ/时间轮是量大后的 L2 实现替换(守门不变),
不是起步配置。**把调度问题降级为数据问题,是本设计的核心**。

## 工程细节

- **游标批量(keyset)**:单轮 `batch` 笔(默认 500),满批循环推进——积压按固定速率
  消化,防单轮锁死;JPA 派生查询保持 H2/PG 双兼容。
- **幂等**:收敛 UPDATE 条件限定 `status='CREATED'`,多实例并发执行无重复副作用;
  回调重推由账本 refId 兜底。
- **可观测**:`jinguan.payment.expiry.converged`(累计收敛)/`.scan`(耗时直方图)/
  backlog(每轮上报存量)。
- **配置**:`order-ttl-minutes`(渠道语义 TTL)/`expiry-scan-seconds`(间隔)/
  `expiry-batch`(单轮上限)。

## 演进触发条件

| 信号 | 动作 |
|---|---|
| 订单 > 万/天,扫描轮次明显增多 | L2 替换为 RocketMQ 延迟消息(下单时发延迟消息,触发同一收敛入口) |
| 多实例部署 | @Scheduled 加 ShedLock,或按实例 id 分片扫描 |
| 真实 PSP 接入 | 渠道侧订单自带过期语义,守门逻辑不变;"漏单"(渠道侧过期后仍支付成功)按渠道回调为准补单入账,登记对账项 |
