# 设计：控制面持有待结算责任

## D1：可靠接收与资金完成分开

木牛负责运输及网络失败续传；锦官负责收到用量后的资金结算。HTTP 2xx 的前提是该批需要处理的用量已经可靠落库，不表示每行都已扣钱。保留现有行字段、状态码体系及 IngestResult 五种处理计数；后台恢复不伪造新的 ingest 调用或累加接收计数。

每行先校验身份与不可变事实、可靠预留明细，再通过 WalletService 尝试扣款，最后更新结果。存储失败不得返回可靠接收成功。存储故障与同 ID 不同事实继续走现有非 2xx 错误；此前已提交的行不能回滚。业务欠费仍逐行跳过，不阻塞同批其他正常行。

## D2：只复用既有明细，不另设结算队列

保留已有 final_outcome，新增 `pending` 表示已接收、尚未完成首次资金处理。候选只有 `pending` 或 `skipped_insufficient` 且已固定 user_id、成功且正费用的行。accepted/replayed 是已结算终态；skipped_free 与 skipped_unbound 不由本件自动恢复器扣款。

尝试计数每次接收或恢复尝试只递增一次，预留与最终投影更新不双计。预留、资金事务、投影更新间允许进程中断，但已落库候选可恢复。扣款成功而投影写失败时，恢复调用既有 usage:{ID} 幂等键修复投影，不产生第二笔扣款。

计费事实固定为首次接收的 key、租户、模型、token、费用、币种、成功状态及源时间等既有镜像事实；比较这些事实后才允许资金操作。同 ID 不同事实报现有幂等冲突，不覆盖旧内容。首次解析出的归属固定；key 后续重绑不能转嫁已有欠费或已结算行。旧记录归属不确定时不得根据当前绑定猜测历史用户。

已有候选回填只选可验证的已绑定欠费行；无法验证的记录保持原态并留明确诊断。索引等必要变更走新迁移；不修改旧迁移或既有资金分录。

恢复轮转使用明细内部的 `last_settlement_attempt_at`，每次实际结算尝试更新。先识别存在候选的用户，再从这些用户全部固定归属明细中取最大尝试时间，包含已成功结算、退出候选的行；只有全部历史均没有实际尝试的用户才按首次优先，再以稳定用户 ID 排序。不能取最小时间或仅聚合候选行，避免大积压用户因剩余未触及行不断重新获得首次优先级。该内部时间不进入请求契约，也不冒充新的 `last_received_at`。

## D3：一个有界周期恢复器

采用现有框架的单实例定时机制，启动后执行首轮、默认每 30 秒一轮；每轮最多 100 个候选用户，每用户最多 100 行。候选用户按最近尝试时间与稳定 ID 排序，避免长期欠费账户占满首批。每用户按首次接收顺序处理，余额不足即保留该行并结束该用户本轮，其他用户继续。

不持明细事务或扫描锁等待钱包事务；候选读取为短事务，所有扣款由 WalletService 的每用户锁与完整资金事务裁决。定时执行不重叠，与在线 ingest 并发仍以同一 refId 收敛。配置异常在启动时明确拒绝，不用无限循环、无界内存积压或第二个重试器。

当前 Mock 回调开启外层事务，`BEFORE_COMMIT` 监听器调用 credit；钱包内部默认 REQUIRED 事务参与外层，但方法的 finally 会在外层物理提交前释放用户锁。本件必须修正这条实际边界：同用户锁持有到拥有该写入的物理事务提交或回滚完成。复用现有事务同步，在参与外层事务时于 `afterCompletion` 释放；没有外层事务时保留覆盖完整钱包操作的 finally，余额不足后的独立停服事务也必须仍在锁内，不能在首个已回滚扣款事务的回调中提前解锁。保留支付状态、分录及停服清除的原子提交，不用 `REQUIRES_NEW` 拆开支付入账。

入账继续在资金事务内解除欠费停服。恢复器下一轮优先结算历史候选；如果充值不足，失败扣款重新置位业务停服，下发名单再按既有拉取周期收敛。这里是有界最终收敛：不承诺“充值响应已经包含全部补扣”，也不把业务停服改成永久吊销。没有待结算项时，既有充值恢复路径保持不变。

周期扫描本身覆盖所有入账来源与重启漏通知，本件不新增通用入账事件。Mock 支付和管理员入账均通过现有 WalletService，使用同一恢复器。

## D4：先幂等裁决，后新扣款余额检查

在每用户锁和完整事务内先查 refId：同用户、金额、原因的既有分录返回重放；载荷冲突拒绝且零新增分录。只有不存在分录时才检查新扣款后的非负余额。重放不能因为当前余额不足被停服。

锁的范围按物理事务完成判定，不按 `TransactionTemplate.execute` 或钱包方法返回判定。Mock 充值与恢复并发时，恢复必须在同用户已提交的资金状态上判断；不能先读充值前余额，再在充值提交之后写回过期的停服决定。异常和回滚路径也必须释放锁。

在线 ingest 与恢复器先核对明细事实、固定归属，再调用这一通道；禁止直接写 ledger_entries。既有分录是资金真相，accepted/replayed 投影都不能被后续 skipped_* 降级。投影更新使用条件更新或版本控制，防并发结果倒退。

## D5：呈现与指标沿用现有面

在现有用量页为 pending 增加“待结算”说明；skipped_insufficient 说明充值后将继续结算。成功恢复更新原行，不产生另一个账单。已有已结算状态显示与费用单位保持。

钱包指标继续落在唯一资金通道；ingest.rows 只统计真实接收分类，后台恢复不得装成再接收。恢复失败日志携带定位信息且不吞异常；指标标签不增加用户/usage ID 等无界值。当前指标与明细查询足以验收，本件不建新看板。

## 验证矩阵

必须覆盖：欠费→200→木牛缓冲结束→Mock 充值→仅一次补扣；管理员充值；充值仍不足；Mock 外层支付事务与恢复可控交错、提交/回滚后锁释放；重启；预留后中断；已扣后投影中断；已结算但低余额重放；相同 ID 不同事实；key 重绑；在线与恢复并发；坏行不阻塞其他用户。使用可驱动的扫描入口测试，不靠真实 sleep 等待。

主规格只在实现验证后同步。本次是提案，所有代码、迁移、端到端与运行验收任务均待执行。
